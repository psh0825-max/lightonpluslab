실기기 없이 iOS 인앱결제 검증하기 — 시뮬레이터 샌드박스 로그인 실패와 SKTestSession

2026-11-09 · LightOn Plus Lab

인앱결제 코드를 고친 날, 정작 결제를 눌러볼 아이폰이 손에 없었습니다. 원격으로 작업하던 중이라 쓸 수 있는 건 Mac 한 대와 iOS 시뮬레이터뿐이었습니다. 시뮬레이터에 샌드박스 계정으로 로그인해서 사보면 되겠다고 생각했는데, 바로 거기서 막혔습니다.

그 뒤로 자리 잡은 방법은 앱 호스티드 테스트 + SKTestSession을 xcodebuild만으로 돌리는 것입니다. 거기까지 가는 과정과, 이 방식으로 확인할 수 없는 것의 경계를 함께 적었습니다. 경계를 모른 채 "시뮬레이터에서 다 통과했다"고 믿으면 서버의 영수증 검증처럼 정말 위험한 부분을 건너뛰게 됩니다.

증상: 결제 시트의 로그인이 계속 튕긴다

Capacitor로 만든 앱의 iOS 빌드에서 구독 버튼을 누르면 시스템 결제 시트가 "Sign in to Apple Account"를 요구합니다. App Store Connect에서 만든 샌드박스 테스터 계정을 넣으면 이렇게 거절됩니다.

AMSErrorDomain 100 Authentication Failed / Password reuse not available

처음엔 비밀번호나 테스터 계정 상태를 의심했습니다. 그런데 테스터를 새로 만들어 넣어도 같은 오류가 났고, 기존 계정이든 새 계정이든 결과가 같았습니다. 결정적인 단서는 같은 계정이 실기기에서는 정상으로 로그인된다는 사실이었습니다. 문제는 계정이 아니라 시뮬레이터라는 환경이었습니다.

Apple 문서도 샌드박스 테스트를 기기 기준으로 설명합니다. 개발 서명 앱에서 처음 구매를 시도하면 iOS 설정 > 개발자에 샌드박스 계정 항목이 생기고 거기서 로그인하는 흐름입니다. 시뮬레이터에서 이 로그인이 된다고 기대할 근거는 문서에 없었습니다. 그래서 로그인을 고치는 대신 로그인이 필요 없는 테스트 환경으로 방향을 바꿨습니다.

선택지: 로컬 StoreKit 테스트 환경

Apple이 제공하는 인앱결제 테스트 환경은 셋입니다. Xcode의 StoreKit Testing, 샌드박스, 그리고 샌드박스를 쓰는 TestFlight입니다. 이 중 StoreKit Testing in Xcode는 App Store 서버에 연결하지 않는 로컬 환경입니다. 상품 정보를 .storekit 파일에 적어두면 앱의 StoreKit 호출이 그 데이터를 쓰고, 거래도 로컬에서 만들어집니다. 로그인이 필요 없고 시뮬레이터에서도 동작합니다.

처음부터 기억해 둘 점이 하나 있습니다. 이 환경이 만드는 영수증과 JWS 거래는 App Store가 아니라 Xcode가 서명합니다(Apple의 테스트 환경 비교). 이 한 줄이 뒤에 나올 "검증할 수 없는 것"을 거의 다 결정합니다.

방법 1: 스킴의 Run 액션에 .storekit 연결하기

기본 방법은 스킴 편집기의 Run 액션 > Options > StoreKit Configuration에서 파일을 고르는 것입니다. .storekit의 상품 ID, 구독 그룹, 가격은 App Store Connect와 똑같이 적었습니다. 스토어프론트와 로케일도 정할 수 있어서, 시뮬레이터 샌드박스에서 달러로 나오던 가격을 원화로 볼 수 있었습니다.

스킴 파일을 직접 다루거나 XcodeGen으로 생성하면 결과는 이렇게 생깁니다.

<!-- App.xcodeproj/xcshareddata/xcschemes/App.xcscheme -->
<LaunchAction buildConfiguration = "Debug" ...>
   ...
   <StoreKitConfigurationFileReference
      identifier = "../../App.storekit">
   </StoreKitConfigurationFileReference>
</LaunchAction>

# XcodeGen 이라면 project.yml 의 스킴에
schemes:
  App:
    run:
      config: Debug
      storeKitConfiguration: App/Support/Products.storekit

여기서 첫 번째 함정을 밟았습니다. identifier의 상대 경로 기준이 직관과 다릅니다. 스킴 파일은 xcshareddata/xcschemes/ 안에 있지만, 제가 동작을 확인한 두 프로젝트 모두 ../../가 .xcodeproj를 담고 있는 폴더를 가리켰습니다. 처음에 ../App.storekit으로 적었을 때는 오류도 경고도 없이 무시됐고, 앱은 그대로 샌드박스로 가서 다시 로그인 시트를 띄웠습니다. 경로가 틀렸다고 알려주는 장치가 없으므로, 결제 시트에 Apple 계정 로그인이 뜨면 로컬 구성이 적용되지 않은 것으로 판단하는 편이 가장 빠릅니다.

두 번째 함정: xcodebuild로 띄우면 적용되지 않는다

스킴에 파일을 연결한 뒤 평소처럼 xcodebuild로 빌드하고 simctl로 설치·실행했습니다. 결과는 또 샌드박스였습니다. 스킴의 StoreKit 구성은 Xcode IDE에서 Run 했을 때만 적용됩니다. RevenueCat 문서도 같은 한계를 적어 두었습니다. xcodebuild로 앱을 띄우는 도구(flutter run 등)는 스킴의 StoreKit 구성 파일을 쓰지 않는다는 내용입니다. xcodebuild test와 거기서 나온 .xctestrun도 열어봤지만 StoreKit 관련 키는 어디에도 실리지 않았습니다.

기기 없이, 그리고 Xcode 창을 직접 클릭하지 않고 IDE Run을 걸려면 AppleScript가 현실적인 답이었습니다. Xcode의 스크립팅 사전에는 워크스페이스 문서에 보내는 run 명령이 있어서, 현재 활성 스킴과 실행 대상으로 Run 액션을 실행합니다. 아래는 예시입니다.

-- run-in-xcode.applescript (예시)
tell application "Xcode"
    open POSIX file "/path/to/ios/App/App.xcodeproj"
    -- open 의 반환값은 비어 있을 때가 있다(스크립팅 사전에 적힌 알려진 문제)
    set ws to active workspace document
    repeat until loaded of ws
        delay 1
    end repeat
    set r to run ws   -- 완료를 기다리지 않고 바로 돌아온다
end tell

처음 한 번은 macOS가 Xcode 제어에 대한 자동화 권한을 묻습니다. 앱이 정말 Xcode를 거쳐 떴는지는 프로세스 환경 변수로 확인했습니다. Xcode가 띄운 앱 프로세스에는 __XCODE_BUILT_PRODUCTS_DIR_PATHS가 들어 있었습니다.

# 예시: 앱 프로세스 환경 변수에 Xcode 흔적이 있는지
ps -E -p "$(pgrep -f 'App.app/App' | head -1)" | tr ' ' '\n' | grep __XCODE_BUILT_PRODUCTS_DIR_PATHS

이 방식은 실제 화면과 결제 시트를 씁니다. 시트에서 구독 버튼을 한 번 누르면 거래가 끝나고, 결제 SDK의 검증과 권한 부여를 거쳐 앱 잠금이 풀리는 데까지 실제 경로를 탑니다. 화면 흐름이나 스토어 스크린샷 확인에 맞습니다.

RevenueCat을 쓴다면 할 일이 하나 더 있습니다. StoreKit 테스트 인증서를 RevenueCat 앱 설정의 StoreKit testing framework 항목에 올려야 하고, 없으면 Xcode가 서명한 거래가 거부됩니다. 인증서는 .storekit을 연 상태에서 Editor > Save Public Certificate로 저장합니다. Apple 문서 설명대로 체인이 없는 루트 인증서이고, 제 Xcode에 든 것은 발급자와 주체가 모두 StoreKit인 자체 서명 인증서(2040년까지 유효)였습니다.

단점은 Xcode GUI가 떠 있어야 하고, 자동화 권한이 필요하고, 결제 시트를 누르는 단계가 남는다는 점입니다. CI에 넣기에는 무겁습니다.

방법 2: 앱 호스티드 테스트에서 SKTestSession 쓰기

그 뒤 SwiftUI로 만든 구독 앱에서 더 단순한 방법을 찾았습니다. 핵심은 테스트 코드를 앱 프로세스 안에서 돌리는 것입니다.

StoreKitTest 프레임워크의 SKTestSession은 Xcode에서 손으로 바꾸던 StoreKit 테스트 설정을 코드로 제어합니다. 구성 파일로 세션을 만들고 disableDialogs를 켜면 테스트 환경 UI 없이 돕니다. 문제는 이 세션이 어느 프로세스의 StoreKit 호출에 닿느냐였습니다. UI 테스트는 앱과 별개인 테스트 러너 프로세스에서 도는데, 처음에 그쪽에서 세션을 만들었을 때는 앱이 보는 상품 목록에 아무 변화가 없었습니다.

반면 Host Application(TEST_HOST)이 앱으로 지정된 유닛 테스트 번들은 앱 프로세스에 주입되어 실행됩니다. 여기서 세션을 만들면 같은 프로세스의 앱 코드가 부르는 Product.products(for:)와 purchase()가 로컬 구성을 씁니다. Xcode IDE도 AppleScript도 없이 xcodebuild 하나로 상품 로드, 구매, 미완료 거래, 복원까지 돌릴 수 있었습니다.

프로젝트 구성

XcodeGen 기준으로 테스트 타깃 하나를 추가합니다. 실제 설정에서 이름만 바꾸고 줄였습니다.

targets:
  App:
    type: application
    sources:
      - path: App
        excludes:
          - "Support/Products.storekit"   # 앱 번들에는 넣지 않는다

  # 앱 프로세스 안에서 돌아야 SKTestSession 이 앱의 StoreKit 호출에 적용된다
  AppStoreTests:
    type: bundle.unit-test
    platform: iOS
    sources:
      - path: AppStoreTests
      - path: App/Support/Products.storekit
        buildPhase: resources
    dependencies:
      - target: App

schemes:
  App:
    run:
      storeKitConfiguration: App/Support/Products.storekit   # IDE Run 용
    test:
      targets:
        - AppStoreTests

XcodeGen은 앱에 의존하는 유닛 테스트 타깃에 TEST_HOST와 BUNDLE_LOADER를 자동으로 넣습니다. Xcode에서 만든다면 Host Application이 앱으로 잡혀 있는지만 보면 됩니다.

.storekit을 앱 타깃이 아니라 테스트 번들의 리소스로 넣은 것은 출시 빌드에 테스트용 상품 정의가 실리지 않게 하려는 의도입니다. Apple 문서는 init(configurationFileNamed:)의 파일을 "앱 번들에 포함한 파일"로 설명하지만 제 환경에서는 테스트 번들 리소스의 파일도 찾았습니다. 문서에 없는 동작이니 세션 생성이 예외 없이 되는지부터 확인하시길 권합니다.

테스트 코드

먼저 앱 쪽 규칙입니다. 서버가 구매 증명(JWS)을 확인하기 전에는 finish()를 부르지 않습니다. 서버 호출이 실패하면 예외가 나서 finish()까지 가지 않고, 거래는 Transaction.unfinished에 남아 다음 실행 때 다시 보내집니다.

private func deliver(_ result: VerificationResult<Transaction>) async throws {
    guard case .verified(let transaction) = result else { throw StoreError.unverified }
    // 서버가 JWS 를 확인해야 다음 줄로 간다. 실패하면 throw 되어 finish 하지 않는다
    try await api.post("payment/apple/verify",
                       json: ["signedTransactionInfo": result.jwsRepresentation])
    await transaction.finish()
}

테스트는 실제로 쓰는 코드에서 이름만 바꿔 줄였습니다.

import StoreKit
import StoreKitTest
import XCTest
@testable import App

@MainActor
final class StoreTests: XCTestCase {
    private var session: SKTestSession!
    private var expectation: String {
        ProcessInfo.processInfo.environment["STORE_EXPECT"] ?? "rejected"
    }

    override func setUp() async throws {
        session = try SKTestSession(configurationFileNamed: "Products")
        session.disableDialogs = true
        session.clearTransactions()
    }

    override func tearDown() async throws {
        session.clearTransactions()
    }

    // 로그인·서버 없이 돈다: 앱 코드의 상품 ID 가 .storekit 에 모두 있는가
    func test1_productsMatch() async throws {
        await Store.shared.loadProducts()
        for id in Store.allProductIDs {
            let product = try XCTUnwrap(Store.shared.products[id], "\(id) 없음")
            let period = try XCTUnwrap(product.subscription?.subscriptionPeriod)
            XCTAssertEqual(period.unit, id.hasSuffix("yearly") ? .year : .month, id)
            XCTAssertFalse(product.displayPrice.isEmpty, id)
        }
    }

    // 로컬 서버가 필요하다
    func test2_purchasePath() async throws {
        await Store.shared.loadProducts()
        let product = try XCTUnwrap(Store.shared.product(tier: .pro, cycle: .monthly))

        if expectation == "rejected" {
            // 서버가 확인하지 못하면 거래를 끝내지 않아야 다음 실행 때 다시 보낸다
            do {
                _ = try await Store.shared.purchase(product)
                XCTFail("서버가 거절했는데 구매가 완료됨")
            } catch {}
            let stillOpen = try await unfinishedExists(product.id)
            XCTAssertTrue(stillOpen, "서버 확인 전에 거래가 끝남")
            return
        }

        let outcome = try await Store.shared.purchase(product)
        guard case .completed = outcome else { return XCTFail("구매 미완료: \(outcome)") }
        let stillOpen = try await unfinishedExists(product.id)
        XCTAssertFalse(stillOpen, "서버가 받았는데 거래가 끝나지 않음")

        // 거래에 계정이 묶여 있어야 한다
        let latest = await Transaction.latest(for: product.id)
        guard case .verified(let transaction)? = latest else { return XCTFail("거래 없음") }
        XCTAssertEqual(transaction.appAccountToken?.uuidString.lowercased(),
                       Session.current?.userID.lowercased())

        let restored = try await Store.shared.restore()
        XCTAssertTrue(restored, "복원이 구매를 찾지 못함")
    }

    private func unfinishedExists(_ productID: String) async throws -> Bool {
        for await result in Transaction.unfinished {
            if case .verified(let t) = result, t.productID == productID { return true }
        }
        return false
    }
}

첫 번째 테스트는 로그인도 서버도 필요 없습니다. 앱 코드에 박힌 상품 ID가 .storekit에 모두 있는지, 월간·연간 기간이 맞는지만 봅니다. 처음에 상품 ID를 다른 플랫폼의 요금제 이름으로 가정해 넣었다가 App Store Connect에 실제로 등록한 ID에 맞춰 앱 코드, .storekit, 서버 기본값을 한꺼번에 바꾼 적이 있는데, 그런 변경 뒤에 앱과 .storekit이 어긋나지 않았는지를 몇 초 만에 확인할 수 있습니다. .storekit과 App Store Connect가 같은지는 이 테스트가 보지 못하므로 사람이 맞추거나, Xcode 14부터 있는 동기화 구성 파일을 씁니다.

두 번째 테스트는 앞의 finish() 규칙을 검증합니다. 로컬 서버가 503을 돌려주면 구매는 실패하고 거래는 미완료로 남아야 합니다. 서버가 받아 주면 거래가 끝나고, appAccountToken이 사용자 ID와 같고, 복원이 같은 구독을 찾아야 합니다. 실제 코드는 서버의 요금제 값이 바뀌었는지도 봅니다.

어느 시나리오를 돌릴지는 환경 변수로 나눴습니다. xcodebuild는 TEST_RUNNER_ 접두어가 붙은 환경 변수를 접두어를 떼고 테스트 러너 프로세스에 넘깁니다. 호스티드 유닛 테스트에서는 그 러너가 곧 앱 프로세스입니다.

# 예시: 서버가 거절하는 경우(기본값)
xcodebuild test \
  -project App.xcodeproj -scheme App \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro Max' \
  -only-testing:AppStoreTests

# 로컬 서버가 받아 주는 경우
TEST_RUNNER_STORE_EXPECT=accepted xcodebuild test \
  -project App.xcodeproj -scheme App \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro Max' \
  -only-testing:AppStoreTests/StoreTests/test2_purchasePath

돌려보며 알게 된 것

  • 테스트 플랜의 StoreKit 설정은 효과가 없었습니다. .xctestplan에 storeKitConfiguration을 넣어봤지만 xcodebuild 실행에서는 아무 차이가 없었습니다. 코드에서 세션을 만드는 쪽이 확실했습니다.
  • 설정은 시뮬레이터에 남습니다. 이 테스트를 한 번 돌린 시뮬레이터에서는 이후 UI 테스트에서도 상품 가격이 떴습니다. Apple 문서도 테스트 환경은 하나뿐이고 모든 SKTestSession이 같은 환경을 제어한다고 설명합니다. 그래서 clearTransactions()로 시작하고 끝내며, 환경을 바꾸는 테스트는 병렬로 돌리지 않습니다.
  • 시뮬레이터 런타임을 고정해야 합니다. 제가 이 방식을 확인한 환경은 Xcode 26.0.1과 iOS 26.0 시뮬레이터 런타임입니다. Apple 개발자 포럼에는 iOS 26.5 시뮬레이터 런타임에서 Xcode 디버그 세션 밖에서 실행한 SKTestSession이 구성 파일을 저장하지 못한다는 보고가 있고, Apple 측이 알려진 문제라고 답했습니다(포럼 스레드). CI에 넣는다면 런타임을 명시적으로 고정하고, 런타임을 올릴 때 이 테스트부터 돌려보는 편이 안전합니다.

권하고 싶은 단언이 하나 더 있습니다. 위 코드에는 없지만, 구매 직후 transaction.environment == .xcode를 확인해 두면 구성이 조용히 빠져 샌드박스로 새는 경우를 테스트가 바로 잡습니다. AppStore.Environment에는 production, sandbox, xcode 세 값이 있고 iOS 16부터 쓸 수 있습니다.

로컬 환경이 오히려 나은 경우도 있습니다. Apple 비교표에 따르면 강제 StoreKit 오류, 승인 요청(Ask to Buy)의 승인·거절, 구독 가격 인상 시험은 샌드박스에서는 안 되고 Xcode 환경에서만 됩니다. SKTestSession의 failTransactionsEnabled, askToBuyEnabled, expireSubscription(productIdentifier:), refundTransaction(identifier:)로 이런 시나리오를 코드로 만들 수 있습니다.

서버 검증은 여기서 끊긴다

Xcode가 서명한 JWS는 Apple 루트 인증서 체인 검증을 통과하지 못하고, 제대로 만든 서버라면 거절하는 게 정상입니다. 그래서 구매부터 복원까지의 성공 경로는 로컬 개발 서버에서만 서명 확인을 건너뛰게 해서 돌렸고, 운영 서버의 검증은 건드리지 않았습니다.

Apple의 공식 서버 라이브러리(App Store Server Library)도 이 구분을 갖고 있습니다. 검증기를 Xcode 환경으로 만들면 App Store가 서명한 데이터가 아니라는 이유로 서명 확인을 생략하고, 거래의 environment 값이 검증기 환경과 다르면 INVALID_ENVIRONMENT로 거절합니다. 그러니 Xcode 검증기는 명시적인 개발 플래그 뒤에만 두는 편이 안전합니다. 예시 코드입니다.

// 예시: 환경별 검증기를 두고, Xcode 검증기는 로컬 개발에서만 켠다
import { SignedDataVerifier, Environment, VerificationException, VerificationStatus }
  from '@apple/app-store-server-library'

const verifiers = [
  new SignedDataVerifier(appleRoots, true, Environment.PRODUCTION, bundleId, appAppleId),
  new SignedDataVerifier(appleRoots, true, Environment.SANDBOX, bundleId),
]

// Xcode 검증기는 서명을 보지 않는다
if (process.env.ALLOW_XCODE_IAP === '1' && process.env.NODE_ENV !== 'production') {
  verifiers.push(new SignedDataVerifier([], false, Environment.XCODE, bundleId))
}

export async function verifyTransaction(jws: string) {
  for (const v of verifiers) {
    try {
      return await v.verifyAndDecodeTransaction(jws)
    } catch (e) {
      if (e instanceof VerificationException &&
          e.status === VerificationStatus.INVALID_ENVIRONMENT) continue
      throw e
    }
  }
  throw new Error('no verifier matched the transaction environment')
}

이 플래그가 운영에서 켜지면 누구나 직접 만든 JWS로 구독을 얻게 됩니다. 앱 쪽에도 비슷한 안전장치를 두었습니다. 디버그 빌드는 Info.plist에서 로컬 서버 주소를 읽을 수 있게 했고, 출시 스크립트는 만들어진 IPA 안의 Info.plist에 그 키가 남아 있으면 실패로 멈춥니다.

실제 Apple 인증서 체인 검증과 서버 알림은 결국 샌드박스에서 따로 확인했습니다. TestFlight 빌드를 실기기에 설치해 월간 구독을 사보니, 운영 서버가 이를 Sandbox 환경 구매로 처리했고 SUBSCRIBED 서버 알림이 반영되어 구독 기록이 생겼습니다. TestFlight는 샌드박스를 쓰므로 청구는 되지 않습니다. 이 단계만큼은 기기를 대신할 방법이 없었습니다.

복원 테스트의 함정

RevenueCat을 쓰는 앱에서 복원을 시험하다 헛걸음을 했습니다. 새 사용자로 시작하려고 simctl uninstall로 앱을 지웠더니 다시 깔고 복원을 눌러도 아무것도 나오지 않았습니다. 앱을 지우면 StoreKit 테스트 거래도 같이 사라지기 때문입니다.

필요한 건 "거래는 남고 앱 쪽 사용자만 새로운" 상태였습니다. 앱은 그대로 두고 앱 컨테이너의 Library/Preferences/com.revenuecat.user_defaults.plist만 지우면 RevenueCat이 새 익명 사용자로 시작합니다. 이 상태에서 복원을 누르면 RevenueCat이 권한을 새 사용자에게 옮겨 주고, 구독이 돌아왔다는 안내가 뜨는 것까지 확인할 수 있었습니다.

검증할 수 있는 것과 없는 것

로컬 StoreKit 테스트는 앱과 내 서버 사이의 로직을 검증하는 도구입니다. Apple 서버가 관여하는 부분은 검증하지 못합니다.

상품 ID·기간·표시 가격·통화가능가격은 .storekit의 자리표시 값이라 실제 가격 등급과 무관

가족 공유는 따로 적어 둘 만합니다. .storekit에도 상품별 Family Sharing 표시가 있지만, Apple이 안내하는 가족 공유 테스트는 App Store Connect에서 샌드박스 테스트 가족을 만들고 구성원 계정마다 로그인해 확인하는 방식입니다. 공유받은 쪽의 familyShared 거래와 공유 해제 시의 회수를 보려면 샌드박스 로그인이 되는 기기가 필요하고, 그게 없다면 이 항목은 미검증으로 남겨 두는 게 정직합니다.

체크리스트

  • 시뮬레이터에서 결제 시트가 Apple 계정 로그인을 요구하면 로컬 구성이 적용되지 않은 것이다. 계정을 의심하기 전에 실행 경로부터 본다.
  • 스킴의 StoreKitConfigurationFileReference는 ../../가 .xcodeproj를 담은 폴더를 가리켰다. 틀려도 경고가 없다.
  • 스킴의 StoreKit 구성은 Xcode IDE Run에서만 적용된다. xcodebuild, simctl launch, flutter run은 샌드박스로 간다.
  • 헤드리스로 돌리려면 Host Application이 앱인 유닛 테스트에서 SKTestSession을 만든다. UI 테스트 러너에서 만든 세션은 앱에 닿지 않았다.
  • .storekit은 테스트 번들 리소스에 두고, 출시 빌드에 실리지 않았는지 확인한다.
  • 테스트에서 transaction.environment == .xcode를 단언해 샌드박스로 새는 경우를 잡는다.
  • 시뮬레이터 런타임을 고정하고, 런타임을 올리면 이 테스트부터 돌린다.
  • 서버의 Xcode 거래 허용은 개발 플래그 뒤에만 두고, 운영에서 켜질 수 없게 막는다.
  • 서명 체인 검증, 서버 알림, 가족 공유는 TestFlight나 실기기 샌드박스로 따로 확인한다. 로컬 테스트 통과를 그 근거로 쓰지 않는다.

지금은 결제 코드를 고치면 xcodebuild로 이 테스트부터 돌리고, 서버 서명과 알림처럼 Apple 서버가 끼는 부분만 TestFlight 빌드로 한 번 더 확인합니다. 두 단계가 각자 무엇을 보증하는지 섞지 않는 한, 기기 없이도 결제 코드를 꽤 자신 있게 고칠 수 있습니다.
