flutter_local_notifications 예약 알림이 안 뜰 때 — 원인 4가지와 점검표

2026-11-09 · LightOn Plus Lab

라이트온 AI 노트는 강의 노트에서 플래시카드를 만들어 간격 반복으로 복습하게 하는 앱이고, 설정에서 켜 두면 매일 정한 시각에 복습할 때를 알려 주는 복습 알림이 있습니다. 그런데 이 알림은 안드로이드에서 기능을 넣은 뒤로 한 번도 뜬 적이 없었고, iOS에서는 토글이 켜지지도 않았습니다. 따라가 보니 원인은 넷이었고, 모두 에러 메시지 하나 없이 조용히 어긋나는 종류였습니다.

증상

예약은 flutter_local_notifications 17.2.4의 zonedSchedule로 합니다. 매일 반복은 matchDateTimeComponents로 걸고, 안드로이드는 정확한 알람 권한이 필요 없는 inexact 모드를 씁니다.

await _plugin.zonedSchedule(
  _dailyReviewId,
  _title,
  _body,
  _nextInstanceOf(hour, minute),
  details,
  androidScheduleMode: AndroidScheduleMode.inexactAllowWhileIdle,
  uiLocalNotificationDateInterpretation:
      UILocalNotificationDateInterpretation.absoluteTime,
  matchDateTimeComponents: DateTimeComponents.time,
);

안드로이드에서는 토글을 켜고 시각을 골라도 그 시각에도, 다음 날에도 알림이 오지 않았습니다. iOS에서는 토글을 누르면 설정에서 알림을 허용하라는 안내만 떴는데, 정작 시스템 권한 창은 한 번도 나온 적이 없었습니다.

먼저 가를 것: 알람이 울렸나, 알림이 게시됐나

안드로이드의 예약 알림은 두 단계로 움직입니다. 플러그인이 AlarmManager에 알람을 걸고, 시각이 되면 시스템이 브로드캐스트한 인텐트를 플러그인의 리시버가 받아 알림을 게시합니다. 알림이 안 뜨면 어느 단계에서 끊겼는지부터 갈라야 합니다.

문제의 1.2.8을 릴리스 빌드로 다시 만들어 API 36 에뮬레이터에 깔고, 시계를 건드리지 않은 채 설정 화면에서 알림 시각을 3분 뒤로 잡았습니다.

$ adb shell dumpsys alarm | grep -A3 'ailecturenote}'
  tag=*walarm*:com.lightonpluslab.ailecturenote/com.dexterous.flutterlocalnotifications.ScheduledNotificationReceiver
  type=RTC_WAKEUP origWhen=2026-10-16 14:37:00.000 window=+2m15s896ms repeatInterval=0 ...

알람은 걸렸고, 시각이 지나자 대기 목록에서 사라졌으며, 같은 출력의 알람 통계에는 1 wakes 1 alarms로 전달된 기록이 남았습니다. 알람은 울렸습니다. 그런데 게시된 알림은 0건이었습니다.

$ adb shell dumpsys notification --noredact | grep -c 'pkg=com.lightonpluslab.ailecturenote'
0

이것만으로 도즈·배터리 최적화(전달 기록이 있음)와 inexact 지연(창이 끝났음)은 빠집니다. 알람은 울렸는데, 그걸 받아 알림을 만드는 쪽이 일하지 않은 겁니다. logcat을 앱과 플러그인 이름으로 걸러 봐도 관련된 줄은 없었습니다.

원인 1: 아무도 받지 않는 브로드캐스트

dumpsys의 tag가 가리키는 대상은 ScheduledNotificationReceiver라는 명시적 컴포넌트입니다. 그런데 빌드된 APK의 매니페스트에는 플러그인 이름이 한 번도 나오지 않았습니다.

$ aapt2 dump xmltree --file AndroidManifest.xml app-1.2.8.apk | grep -c -i flutterlocalnotifications
0

이 플러그인은 16 버전부터 자기 매니페스트에 VIBRATE와 POST_NOTIFICATIONS만 선언하고, 예약 알림에 필요한 리시버 두 개는 앱이 직접 넣도록 README에 적어 둡니다. 처음 기능을 넣을 때 그 절을 놓쳤습니다. 명시적 인텐트의 대상이 매니페스트에 없으니 브로드캐스트는 갈 곳이 없고, 실행되지 않은 플러그인 코드는 예외도 로그도 남기지 않습니다.

다음 날 알람이 생기지 않은 것도 같은 이유입니다. 안드로이드에서 매일 반복은 운영체제의 반복 알람이 아닙니다. 한 번짜리 알람을 받은 리시버가 알림을 띄운 직후 다음 회차를 직접 다시 겁니다.

// flutter_local_notifications 17.2.4, ScheduledNotificationReceiver.onReceive
FlutterLocalNotificationsPlugin.showNotification(context, notificationDetails);
FlutterLocalNotificationsPlugin.scheduleNextNotification(context, notificationDetails);

수정은 README에 적힌 그대로입니다.

<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED"/>

<!-- <application> 안 -->
<receiver
    android:exported="false"
    android:name="com.dexterous.flutterlocalnotifications.ScheduledNotificationReceiver" />
<receiver
    android:exported="false"
    android:name="com.dexterous.flutterlocalnotifications.ScheduledNotificationBootReceiver">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED"/>
        <action android:name="android.intent.action.MY_PACKAGE_REPLACED"/>
        <action android:name="android.intent.action.QUICKBOOT_POWERON" />
        <action android:name="com.htc.intent.action.QUICKBOOT_POWERON"/>
    </intent-filter>
</receiver>

RECEIVE_BOOT_COMPLETED는 다른 플러그인이 병합해 오고 있었지만, 그 플러그인이 빠지는 날 부트 리시버가 다시 조용히 죽지 않도록 직접 선언했습니다. 플러그인이 런타임에 이름으로 찾는 알림 아이콘 @mipmap/ic_launcher도 리소스 축소기가 지우지 않게 res/raw/keep.xml에 넣었습니다. README는 아이콘이 지워지면 알림이 조용히 실패할 수 있다고 경고합니다.

원인 2: 리시버를 넣어도 돌아오지 않은 알림

여기서 끝난 줄 알았습니다. 그런데 1.2.8에서 알림을 켜 둔 채 업데이트하는 경우를 재현하자 결과가 이상했습니다. 리시버를 넣은 빌드를 adb install -r로 덮어 설치하자 부트 리시버가 실행된 흔적은 logcat에 찍혔는데, dumpsys alarm에는 알람이 없었습니다.

I/ActivityManager: Start proc ...:com.lightonpluslab.ailecturenote/... for broadcast
  {com.lightonpluslab.ailecturenote/com.dexterous.flutterlocalnotifications.ScheduledNotificationBootReceiver}

플러그인은 예약한 알림의 사본을 SharedPreferences에 Gson JSON으로 저장하고, 부트 리시버는 재부팅이나 업데이트 때 그 사본으로 알람을 다시 겁니다. AlarmManager 문서에 적혀 있듯 알람은 재부팅하면 지워지므로 플러그인에게는 이 사본이 유일한 복구 수단입니다. 사본은 이렇게 읽습니다.

// flutter_local_notifications 17.2.4, loadScheduledNotifications
Type type = new TypeToken<ArrayList<NotificationDetails>>() {}.getType();
scheduledNotifications = gson.fromJson(json, type);

가장 유력하게 본 용의자는 이 TypeToken입니다. TypeToken은 익명 하위 클래스에 남은 제네릭 시그니처를 리플렉션으로 읽는데, AGP 8.0부터 기본인 R8 full mode는 -keepattributes Signature가 있어도 keep 규칙에 걸린 클래스에만 시그니처를 남깁니다. 시그니처를 잃은 TypeToken은 이렇게 시작하는 예외를 던집니다.

TypeToken must be created with a type argument: new TypeToken<...>() {};

앱 빌드가 쓰던 Gson 2.10.1 jar에는 R8 규칙이 들어 있지 않고(2.11.0부터 META-INF/proguard/gson.pro가 포함됩니다), README도 플러그인 v18 이하는 Gson 규칙을 앱이 직접 넣으라고 안내합니다. 1.2.8의 앱 규칙 파일에는 Gson 규칙이 없었습니다. 이 가설대로라면 순서는 이렇습니다. 앱은 예약 전에 항상 cancel을 부르고, cancel은 저장본이 없으면 TypeToken을 거치지 않고 빈 목록 []을 씁니다. 이어지는 zonedSchedule은 알람을 먼저 건 뒤 사본을 저장하려고 그 []을 읽다가 예외를 내고, 예외는 Dart로 올라와 NotificationService의 catch에서 사라집니다. 알람은 걸리고 사본은 빈 채로 남습니다.

다만 이 가설은 끝까지 확인하지 못했습니다. 릴리스 빌드는 run-as가 막혀 사본 파일을 열어 볼 수 없었고, 1.2.8의 R8 매핑도 남아 있지 않았습니다. 게다가 1.2.8에는 모든 내부 클래스를 지키는 넓은 규칙(-keep class **.*$* { *; })이 있었고 익명 TypeToken 하위 클래스도 여기에 걸리므로, 시그니처가 정말 지워졌다고 단정할 수는 없습니다. 확인된 것은 1.2.8에서 켠 알림이 부트 리시버로는 돌아오지 않는다는 사실, 그리고 Gson 규칙이 들어간 빌드에서는 재부팅 복구가 동작한다는 결과입니다.

원인이 어느 쪽이든 대응은 같았습니다. 지난 버전이 플러그인 사본에 남긴 상태는 새 버전의 규칙으로 고칠 수 없습니다(Gson 규칙은 1.2.9에서 이미 추가돼 있었습니다). 그래서 앱이 가진 진실의 원천, 즉 설정 화면이 Hive에 저장한 켜짐 여부와 시각으로 매 실행마다 다시 예약하게 했습니다. 같은 ID를 취소하고 다시 거는 동작이라 여러 번 불러도 안전합니다.

// main.dart, 시작 시
await NotificationService.init();
unawaited(NotificationService.restoreDailyReviewReminder());

// NotificationService
static Future<void> restoreDailyReviewReminder() async {
  final enabled =
      DatabaseService.getSetting<bool>(enabledSettingKey) ?? false;
  if (!enabled) return;
  await scheduleDailyReviewReminder(
    hour: DatabaseService.getSetting<int>(hourSettingKey) ?? defaultHour,
    minute:
        DatabaseService.getSetting<int>(minuteSettingKey) ?? defaultMinute,
  );
}

코드 경로상 예상되는 부수 효과도 하나 있습니다. 1.2.9에서 켠 알림은 사본은 남지만 리시버가 없어 그 시각이 과거에 멈춰 있습니다. 업데이트 순간 부트 리시버가 그 과거 시각으로 알람을 걸면 AlarmManager는 문서대로 즉시 울리므로, 지난 알림이 한 번 뜰 수 있습니다. 해롭지 않다고 보고 두었습니다.

원인 3: 서울에 고정된 시간대

리시버가 생기자 가려져 있던 문제가 드러났습니다. 기기 시간대를 읽는 함수가 나중에 채울 자리로 남은 채 서울을 돌려주고 있었습니다.

static Future<String> _localTimeZoneName() async {
  // Without a dedicated tz plugin we cannot reliably read the device zone,
  // so we use the app's primary locale zone. Kept as a hook for future use.
  return 'Asia/Seoul';
}

timezone 패키지는 기기 시간대를 알려 주지 않으므로, README 안내대로 플랫폼 채널이나 flutter_timezone 같은 패키지로 얻어 tz.setLocalLocation에 넣어야 합니다. 이 이름은 첫 회차만 정하지 않습니다. 플러그인의 안드로이드 코드는 ZoneId.of(timeZoneName)로 매일의 다음 회차를 그 시간대에서 계산하고, iOS도 반복 트리거에 그 시간대를 넣습니다. 캘리포니아에서 20:00으로 맞춘 알림이 현지 새벽 4시에 울리는 구조였지만, 알림이 아예 안 울리던 동안에는 보일 리 없었습니다.

플러그인을 더하지 않고, 앱이 이미 쓰던 MethodChannel 패턴으로 기기 시간대를 넘겼습니다. 안드로이드는 TimeZone.getDefault().id, iOS는 TimeZone.current.identifier를 돌려줍니다. 받은 이름이 IANA DB에 없으면 서울로 떨어집니다. 자바 TimeZone은 GMT+09:00 같은 사용자 지정 ID도 허용하기 때문입니다.

// MainActivity.kt
MethodChannel(flutterEngine.dartExecutor.binaryMessenger, timeZoneChannelName)
    .setMethodCallHandler { call, result ->
        when (call.method) {
            "getLocalTimeZone" -> result.success(TimeZone.getDefault().id)
            else -> result.notImplemented()
        }
    }

// notification_service.dart
@visibleForTesting
static tz.Location locationFor(String? name) {
  if (name != null) {
    try {
      return tz.getLocation(name);
    } on tz.LocationNotFoundException {
      // fall through
    }
  }
  return tz.getLocation(_fallbackTimeZone);
}

이 함수에는 옛 ID인 Asia/Calcutta, 빈 값, GMT+09:00을 포함한 단위 테스트 네 개를 붙였습니다. 매 실행 재예약 덕분에 여행으로 시간대가 바뀌어도 다음에 앱을 열면 알림이 새 시간대로 옮겨집니다.

원인 4: iOS는 처음부터 연결돼 있지 않았다

iOS는 두 누락이 겹쳤습니다. 초기화에 iOS 설정을 넘기지 않아 플러그인이 ArgumentError('iOS settings must be set when targeting iOS platform.')를 던졌고, 앱 시작을 막지 않으려고 모든 예외를 잡던 init()이 이를 삼켰습니다. 또 권한 요청이 안드로이드 구현만 찾아서 iOS에서는 묻지도 않고 false를 돌려줬고, 설정 화면은 그걸 거부로 읽었습니다. 고친 것은 넷입니다.

  • DarwinInitializationSettings를 넘기되 권한 요청은 모두 false로 두어, 앱을 열 때가 아니라 토글을 켤 때 권한 창이 뜨게 했습니다.
  • 안드로이드 구현이 없으면 IOSFlutterLocalNotificationsPlugin의 requestPermissions(alert: true, sound: true)를 부릅니다.
  • 예약할 때 DarwinNotificationDetails를 함께 넣습니다.
  • AppDelegate에서 UNUserNotificationCenter.current().delegate = self를 설정했습니다. README가 요구하는 부분이고, iOS는 따로 설정하지 않으면 앱이 포그라운드일 때 알림을 표시하지 않습니다.
const darwinSettings = DarwinInitializationSettings(
  requestAlertPermission: false,
  requestSoundPermission: false,
  requestBadgePermission: false,
);
const initSettings = InitializationSettings(
  android: androidSettings,
  iOS: darwinSettings,
);

iOS에서는 플러그인이 UNCalendarNotificationTrigger를 반복으로 등록해 운영체제가 매일 반복을 처리합니다. 안드로이드식 리시버나 부트 복구는 필요 없고, 시작 시 재예약은 시간대를 현재 값으로 옮기는 역할만 합니다.

검증

원인 2의 용의자가 R8이라 축소를 하지 않는 디버그 빌드로는 재현을 믿을 수 없습니다. 그래서 안드로이드는 전부 릴리스 빌드로 확인했고, 시계를 돌리는 대신 알림 시각을 2~3분 뒤로 잡았습니다.

시나리오결과
1.2.8, 3분 뒤 예약알람은 전달, 게시된 알림 0건, 다음 날 알람 없음
1.2.8에서 켠 채 리시버만 넣은 빌드로 업데이트부트 리시버는 실행, 크래시 없음, 복구된 알람 없음
시작 시 재예약 빌드로 업데이트 후 실행다음 날 같은 시각 알람 복구
14:56 예약14:57 무렵 게시, 다음 날 14:56 알람 자동 생성
재부팅앱을 열지 않아도 알람 복구, Gson 관련 오류 없음
로스앤젤레스 시간대수정 전 14:56 알림이 현지 22:56, 수정 후 현지 14:56. 현지 00:33 예약은 00:33에 게시
앱을 멈춘 채 서울 시간대로 바꾸고 실행다음 알람이 서울 00:33으로 이동
iOS 시뮬레이터, 로스앤젤레스 시간대권한 창, 포그라운드 배너, 백그라운드 알림 모두 현지 시각에 표시
 
# 산출물 매니페스트에 리시버가 있는지
aapt2 dump xmltree --file AndroidManifest.xml app-release.apk | grep -c -i flutterlocalnotifications

# 걸린 알람과 창, 실제 게시 여부
adb shell dumpsys alarm | grep -A3 '<패키지명>}'
adb shell dumpsys notification --noredact | grep -A3 'pkg=<패키지명>'

# 업데이트 경로: 옛 버전에서 알림을 켠 뒤 덮어 설치 / 재부팅 경로
adb install old.apk
adb install -r new.apk
adb reboot

# 시간대
emulator -avd <AVD 이름> -timezone America/Los_Angeles
adb shell settings put global auto_time_zone 0
adb shell cmd alarm set-timezone Asia/Seoul

# iOS 시뮬레이터: 앱 프로세스에만 TZ를 넣는다(시스템 시계는 맥 기준)
SIMCTL_CHILD_TZ=America/Los_Angeles xcrun simctl launch <UDID> <번들 ID>

몇 가지를 덧붙입니다.

  • inexact 창은 넓습니다. 3분 뒤 알람의 창은 +2m15s, 다음 날 알람의 창은 +1h였습니다. 안 뜬다고 판단하기 전에 창이 끝났는지부터 봅니다.
  • 업데이트는 별도의 경로입니다. 새로 설치해서 켜는 테스트만 했다면 원인 2는 보이지 않았습니다.
  • 강제 종료는 결과를 흐립니다. 시간대를 바꾸고 앱을 강제 종료한 직후에는 대기 알람이 목록에 없었습니다. 어느 쪽이 지웠는지는 나눠 보지 않았지만, 다시 실행하자 재예약 코드가 새 시간대로 알람을 걸었습니다.
  • SIMCTL_CHILD_TZ는 앱 프로세스의 시간대만 바꿉니다. 현지 01:00 알림이 맥 시계로 17:00에 떴습니다. 시뮬레이터는 릴리스 빌드를 돌리지 못해 동작은 디버그 빌드로 봤습니다.

예약 알림을 넣을 때 쓰는 점검표

안드로이드

  • 빌드 산출물(병합된 매니페스트나 APK)에 ScheduledNotificationReceiver와 ScheduledNotificationBootReceiver가 있는가.
  • RECEIVE_BOOT_COMPLETED를 앱 매니페스트에 직접 선언했는가.
  • 정확한 시각이 꼭 필요한가. 필요하면 SCHEDULE_EXACT_ALARM과 requestExactAlarmsPermission(), 또는 스토어 심사 대상인 USE_EXACT_ALARM이 필요합니다. README에 따르면 정확한 알람 권한이 취소되면 반복 알림의 다음 회차도 예약되지 않습니다.
  • Android 13 이상에서 POST_NOTIFICATIONS를 런타임에 요청하는가.
  • 플러그인 v18 이하라면 Gson 규칙을 넣었는가. 릴리스 빌드에서 재부팅 후 알람이 복구되는지로 확인합니다.
  • 알림 아이콘을 이름으로 넘긴다면 keep.xml로 지켰는가.
  • 백그라운드 실행을 막는 제조사 기기(README의 Caveats)를 도움말에 안내했는가.

iOS

  • InitializationSettings에 iOS:를 넘겼는가.
  • 권한 요청이 iOS 구현도 부르는가.
  • AppDelegate에서 UNUserNotificationCenter delegate를 설정했는가.

공통

  • tz.setLocalLocation()에 기기 시간대를 넣고, 모르는 ID에 대비했는가.
  • 플러그인 사본이 아니라 앱 설정을 진실의 원천으로 두고, 시작할 때마다 다시 예약하는가.
  • 알림 관련 예외를 삼키더라도 어딘가에 남기는가. 이번 iOS 초기화 실패는 앱 코드의 catch에서 흔적 없이 사라졌습니다.
  • 새 설치뿐 아니라 업데이트, 재부팅, 시간대 변경을 각각 릴리스 빌드로 돌려 봤는가.

남는 교훈

예약 호출의 성공은 알림의 성공이 아닙니다. 알람이 울리는지, 누가 받는지, 받은 쪽이 다음 회차를 거는지는 별개의 단계입니다. dumpsys alarm과 dumpsys notification을 나란히 보면 어디서 끊겼는지가 바로 갈립니다.

시작을 막지 않되, 기록은 남겨야 합니다. 부가 기능의 실패가 앱 시작을 막으면 안 된다는 판단은 맞았지만, 삼킨 예외가 아무 데도 남지 않으면 그 기능은 몇 달이고 죽은 채로 출시됩니다.

문제는 겹쳐서 숨습니다. 시간대 버그는 알림이 울리지 않는 동안 보이지 않았습니다. 하나를 고치면 그 수정이 새로 연 경로를 곧바로 돌려 봐야 합니다.
